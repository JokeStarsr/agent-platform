# 设计文档治理规范（DESIGN DOCUMENT POLICY）

> 版本：v1.0 ｜ 状态：生效 ｜ 依据：《企业级智能体平台架构设计说明书》第 6 章数据架构、第 7 章质量保障

---

## 1. 目的

本项目实行**设计先行**：凡属"重要设计"，必须先产出设计文档、经用户检查通过后，才能开始编码实现。
目的有三：

1. **可检查**：用户在代码落地前就能审查设计意图，避免"代码写完才发现方向错了"。
2. **可追溯**：任何表结构、接口、架构决策都能回溯到"为什么这么设计"。
3. **可传承**：设计理由不随会话丢失，AI 换会话后仍能保持一致。

---

## 2. 适用范围（哪些算"重要设计"）

以下变更**必须**先写设计文档：

| 类别 | 示例 | 使用模板 |
|------|------|----------|
| **新建/修改表结构** | 新增 `t_chat_session` 表、给表加字段、改字段类型、加索引 | `templates/TABLE-DESIGN-TEMPLATE.md` |
| **接口契约** | 新增 REST API、修改请求/响应结构、MCP 工具签名 | 接口契约模板（后续补充） |
| **架构决策（ADR）** | 选 PGVector 还是 Milvus、自研 DAG 还是引 Temporal | ADR 模板（后续补充） |
| **安全规则** | 注入检测规则、沙箱配置、租户隔离方案 | 安全设计模板（后续补充） |
| **数据治理变更** | 保留策略、脱敏规则、删除策略调整 | 表设计模板 + 专项说明 |

**不需要**设计文档的：纯重构（不改行为）、测试补充、文档修订、依赖升级（无破坏性）。

---

## 3. 文档位置与命名

所有设计文档放在：

```
AgentProduct/agent-platform/docs/design/
├── table/          # 表结构设计
│   └── YYYYMMDD-<表名>.md        例：20260827-t-chat-session.md
├── api/            # 接口契约
├── adr/            # 架构决策记录
└── security/       # 安全设计
```

命名规则：`日期(8位) - 短横线 - 对象名`，全部小写。

---

## 4. 工作流程（四步闸门）

```
① 写设计文档  →  ② 用户检查  →  ③ 通过后实现  →  ④ 不一致时回写文档
```

1. **写**：AI（或开发者）用对应模板起草设计文档，**附逐项说明**（为什么这样设计）。
2. **查**：用户检查。未通过 → 修改后重查；**未获批准禁止写实现代码**。
3. **实现**：检查通过后编码，实现必须与文档一致。
4. **回写**：若实现过程中发现需偏离设计，先回到第①步更新文档并说明原因，再继续。

---

## 5. 设计文档的最低质量要求

一份可被接受的设计文档必须回答以下问题（缺一退回）：

- **为什么**：这个设计解决什么问题？不做会怎样？
- **是什么**：结构/字段/接口逐项列出，每项附一句说明。
- **怎么权衡**：考虑过哪些备选方案？为什么放弃？
- **合规影响**：是否涉及租户隔离、数据血缘、PII 脱敏、保留策略？分别怎么处理？
- **演进**：将来数据量增长或需求变化时，这个设计哪里会先撑不住？

---

## 6. 与检查点的关系

排期文档中每周的"周末检查点"，**新增表结构的周必须把对应设计文档列入检查清单**。
设计文档未通过用户检查，视为该周检查点未通过。
