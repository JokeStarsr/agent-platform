# Golden Set 评测集设计

> 版本：v1.0 ｜ 状态：待用户检查 ｜ 依据：《架构设计说明书》第 7 章评测与质量保障、《开发排期》W3 检查点

---

## 1. 设计目的

**要解决的问题**：P1 收口检查点要求"忠实度 ≥ 0.90、Recall@5 ≥ 0.85、转人工率 ≤ 30%、Golden Set ≥ 80 条进 CI"。当前平台没有任何评测数据资产，无法量化回答质量，也无法阻止劣化变更上线。

**不做会怎样**：无评测集 → 无法判断 RAG 管道是否达标 → 无法建立发布门禁 → 变更回归只能靠人肉抽查，项目不满足"质量可度量（G3）"目标。

---

## 2. 数据结构（逐项说明）

### 2.1 存储位置

```
AgentProduct/agent-platform/src/test/resources/golden-set/v1/
├── golden-set.json          # 评测条目（80 条起步）
└── documents/               # 来源文档原文（种子知识库，与线上知识库同源）
    └── *.md / *.txt / *.pdf
```

> 说明：评测集是**测试资源**，随代码库版本化进 CI；来源文档同时用于**离线索引管道**灌库（同源保证"评测文档在库里"这个前提成立）。

### 2.2 条目 schema（golden-set.json）

```json
{
  "version": "1.0",
  "createdAt": "2026-08-27",
  "items": [
    {
      "id": "KB-001",
      "category": "退换货",
      "difficulty": "easy",
      "question": "7天内商品可以无理由退货吗？",
      "expect": {
        "answer": "可以。自签收之日起7日内，商品不影响二次销售即可发起无理由退货。",
        "answerSource": ["tc_policy_v3.md#3.2"],
        "shouldAnswer": true,          // true=知识库有答案; false=故意刁钻,应拒答±转人工
        "confidenceFloor": 0.8         // 期望置信度下限,低于则判转人工逻辑失效
      }
    }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | string | 是 | 唯一编号，格式 `KB-NNN`（可回答）/ `TRAP-NNN`（刁钻）/ `EDGE-NNN`（边界） |
| `category` | string | 是 | 业务分类：退换货 / 物流 / 支付 / 售后 / 会员 / 政策 |
| `difficulty` | enum | 是 | `easy` / `medium` / `hard`，用于分层统计 |
| `question` | string | 是 | 用户问题原文（可含口语化表述、错别字、指代） |
| `expect.answer` | string | 条件 | `shouldAnswer=true` 时必填：标准答案（人工撰写，业务人员定稿） |
| `expect.answerSource` | string[] | 条件 | 标准答案对应的知识文档定位（`文件名#章节`），供引用完整性校验 |
| `expect.shouldAnswer` | bool | 是 | 该条是否期望模型给出答案；false 时 answer 应为空且必须转人工 |
| `expect.confidenceFloor` | float | 是 | 置信度下限（0-1）；忠实度与转人工判定共用 |

### 2.3 评价指标（评测脚本输出）

| 指标 | 定义 | 目标基线（P1 闸门） |
|------|------|---------------------|
| 忠实度 Faithfulness | 答案关键结论是否都可在检索切片中找到依据（LLM-as-judge 打分） | ≥ 0.90 |
| 召回 Recall@5 | 标准答案来源文档是否在 Top-5 检索结果内 | ≥ 0.85 |
| 转人工正确率 | `shouldAnswer=false` 的条目是否都触发拒答/转人工 | 100% |
| 引用完整率 | 关键结论是否标注引用编号 | ≥ 95% |

## 3. 覆盖策略与数量

### 3.1 总量与分布（P1 闸门要求 ≥ 80 条）

| 类型 | 占比 | 数量 | 设计意图 |
|------|------|------|----------|
| 可回答（KB） | 70% | 56 | 覆盖全部 6 个业务分类；easy/medium/hard = 4/4/2 比例 |
| 刁钻（TRAP） | 15% | 12 | 知识库**没有**答案的问题（钓鱼：诱导编造、过时政策、外部信息）→ 必须拒答 |
| 边界（EDGE） | 15% | 12 | 部分相关、指代消解（"它""那包"）、错别字、近义表述 → 检验召回鲁棒性 |

### 3.2 刁钻条目设计要点（转人工率的测试手段）

- TRAP 必须同时满足：库内无直接答案 + 诱导性语气（"你肯定知道吧"）
- 过时政策题：知识库只存 v3 政策，问 v2 旧规 → 应拒答（防止幻觉编旧规）

## 4. 备选方案与放弃理由

| 备选 | 放弃理由 |
|------|----------|
| 紧急问垫用小数据集（如 20 条先跑起来） | 数量不足时 95% 置信区间过宽，闸门判定无统计意义；W3 明确要求 ≥ 80 |
| 直接用 LLM 生成 Golden Set | 标准答案 = 企业的"正确"定义，必须业务人员人工撰写；AI 只能起草提问角度，不能定稿答案（违背排期 1.1 节"业务语料只有你有"） |
| 评测集放数据库而非 JSON | P1 阶段无评测数据写入场景，JSON 进 git 即版本化即 CI 可读；DB 存储留到评测平台（P3）演进时再搬 |

## 5. 合规/租户/血缘/保留策略影响

- **租户隔离**：评测集按 `tenant_id="default"`（平台默认租户）单份维护；多租户试点在 P2 评测平台引入后按租户分目录。
- **数据血缘**：每条 `answerSource` 记录"答案 ← 文档章节"反向血缘，评测报告可按条目回溯来源。
- **PII 脱敏**：评测集为虚构业务问答，不含真实个人数据；若后续引入含真实用户的 badcase，条目必须脱敏后入库（规则写入 `docs/design/security/` 后续版本）。
- **保留策略**：Golden Set 是资产不是日志，随仓库长期保留；每个版本目录不删除旧版（`v1/`、`v2/` 并存），不可变。

---

## 6. 演进与限制（哪里先撑不住）

- **第一期 80 条是下限**：P1 收口后按周在周五 badcase 治理中进新条目，目标是 P2 前 ≥ 200 条。
- **LLM-as-judge 的忠实度**依赖评测用模型（计划用 deepseek-chat 判分）；若判分模型本身漂移，评测报告会误报——届时引入双模型互判（P3 评测平台）。
- **文档「同源」假设**：评测来源文档必须与线上知识库同源，否则 Recall 指标失真 —— 文档一更新，`documents/` 必须同步（写入 W2 文档管道维护清单）。

---

## 7. 实施计划（文档通过后）

1. 建目录 + 写 6 个业务分类的种子文档（`documents/*.md`，每类 2-3 份，含政策类）
2. 按覆盖策略编写 80 条 JSON 条目（我起草问题、你定标准答案）
3. 写评测脚本 v1：`scripts/eval/golden_set_runner.py`（读 JSON → 调 RagService.search → 指标计算 → 输出 markdown 报告）
4. 接入 CI 门禁脚本（P1 检查点：指标低于基线 → 爆红）
