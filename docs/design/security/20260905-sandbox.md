# 执行沙箱设计（L5 工具协议层 · 安全红线）

> 版本：v1.0 ｜ 状态：**已批准**（2026-09-05 用户审批通过，进入实现） ｜ 依据：《开发排期》W12（执行沙箱：代码与 SQL 的安全边界，红线周）、`docs/design/architecture/20260901-tool-engine.md`（W5，已批准）、CLAUDE.md 设计文档铁律

---

## 1. 设计目的

**要解决的问题**：W5 起的工具执行是**进程内直接运行**（`AgentTool.execute` 在主 JVM 里），只对**平台自研信任代码**安全。但 W12 起平台要扩展两类高风险执行：

1. **代码执行**：用户/外部 Agent 提交的**非信任代码**（Python/JS/Shell）需要执行——如 W11 工具市场自注册工具的 HTTP 转发、数据分析脚本（W15 NL2SQL 的验证脚本）。在主 JVM 里跑任意代码 = **任意命令执行 + 逃逸 = 平台被攻陷**。
2. **SQL 执行**：NL2SQL（W15）让模型生成 SQL 查业务库——模型生成的 SQL 可能含**写操作 / 全表扫描 / 注入**。直接连主库执行 = **数据泄露/破坏**。

**不做会怎样**：沙箱是 P3 闸门"沙箱逃逸自测通过（无网络/资源限额/超时回收）"的硬性要求；红线领域漏一条 = 平台被任意代码打穿、业务库被删。违反"安全第一"底线。

**范围**：本设计实现 **L5 执行沙箱 v1**——①代码沙箱（Docker 容器池：无网络/资源限额/只读文件系统/秒级超时强杀，执行任意语言代码）；②SQL 沙箱（只读副本 + AST 白名单 + 强制 LIMIT + 行数/列脱敏）；③安全测试套件（逃逸用例 × 20）；④沙箱审计。**不做**：非容器沙箱（Firecracker/gVisor，量大后演进）、分布式执行引擎、多语言镜像市场（v1 固定 Python/Shell 镜像，扩展按需加镜像）、W15 语义层/NL2SQL 本体。

## 2. 关键架构决策（ADR-20260905-02：容器隔离沙箱 + 独立只读 SQL 通道）

### 2.1 代码沙箱：Docker 一次性容器，非自研 JVM 安全策略

```
非信任代码/命令 ─► SandboxOrchestrator（L5）
   │ 选镜像 → 池中取闲置容器 或 create+start（network none / read-only / 限额）
   │ docker exec -t 执行  → 超时强杀（exec timeout → docker kill 容器）
   │ stdout/stderr 截断回传 → 容器销毁/回池
```

- **为什么用 Docker 而非 Java SecurityManager/ProcessBuilder**：SecurityManager 在 JDK 17 deprecated/未来移除且本身难防逃逸；裸 ProcessBuilder 无资源/网络隔离。Docker 提供网络隔离（`network_mode: none`）、文件系统只读（`--read-only`）、CPU/内存/pids 限额、能力裁剪（`--cap-drop ALL`）、seccomp 默认策略——多层纵深，所有现代沙箱事实标准。
- **一次性 or 池？** v1 用**池化容器**（预热 1-2 个闲置容器，执行后销毁重建。省去每次 0.5-2s 的容器启动），池大小与并发上限绑定（默认 pool=2，maxWait 空池排队）。**宁可排队不放宽隔离**。
- **不做的方向**：gVisor/Firecracker 微虚拟机（隔离更强但复杂，数据量大后可演进）；每个租户独立容器网络（v1 单租户沙箱，租户隔离靠"一次执行一个租户、执行间销毁"）。

### 2.2 SQL 沙箱：只读通道 + AST 白名单双保险

```
SQL（模型生成）──► SqlSanitizer（AST 白名单：
                   仅 SELECT/WITH；拒绝写/DDL/CALL/多语句）
   └─► 只读事务（BEGIN READ ONLY → <sql> → COMMIT/ROLLBACK）
        └─► 只读账号连库（PG 只读角色 + 只读连接参数）
             └─► 结果：行数截断 + 敏感列过滤 + 强制 LIMIT 回填
```

- **纵深防御四层**：①连接层只用**只读账号**（PG 角色 `SELECT` on 授权 schema，无 INSERT/UPDATE/DELETE/DDL 权限）→ 即使绕过解析器也写不成；②事务层每条语句 `BEGIN READ ONLY` 包裹 → 数据库拒绝任何写语句（解析绕过第二道保险）；③解析层 AST 白名单（仅 SELECT/WITH，拒绝多语句、`;` 注入、`FOR UPDATE`）；④结果层行数截断 + 强制 LIMIT。
- **主库经验教训**：v1 直接用平台现有 PG（`agent_platform` 库）做只读通道（`default_transaction_read_only=on` + 只读角色），不引入副本（避免数据分叉、部署复杂度）。**只读角色是硬边界**——它是"即使一切解析失效也写不进去"的最后防线。
- **不做的方向**：只读 Postgres 副本做 SQL 沙箱（数据一致性/部署成本高，数量级增长后再上）；白名单只有解析层（单点失守=裸奔）。

## 3. 代码沙箱设计（CodeSandbox）

### 3.1 镜像与容器定义

| 项 | 值 | 说明 |
|----|----|------|
| 镜像 | `sboxes/python-311`（python + bash + common libs，~100MB） | v1 固定两镜像（python/shell）；其余语言按需加镜像 |
| 网络 | `--network none` | **禁止任何出网**（DNS/TCP/UDP/ICMP 全断） |
| CPU | `--cpus 1.0` | 单核上限 |
| 内存 | `-m 256m --memory-swap 256m` | 硬限 256MB（swap 同值防超分） |
| Pids | `--pids-limit 64` | 防 fork 炸弹 |
| 文件系统 | `--read-only` | 根只读；`/tmp` 挂 tmpfs（`size=16m`）可写 |
| 能力 | `--cap-drop ALL`（隐含 `--security-opt no-new-privileges`） | 无特权提升 |
| 用户 | `--user runner`（uid 10001，非 root） | 文件写受限 |
| 超时 | exec 硬限 8s → `docker kill` 容器 | **强杀而非优雅**（防超时后继续跑） |
| 输出 | stdout/stderr 各上限 16KB 回传 | 防刷屏 |

### 3.2 执行流程

```
POST /api/sandbox/code  {language, code, args?, stdin?}
  1. 校验 language ∈ {python, shell}；code ≤ 32KB；非空
  2. 池取闲置容器（无 → 等待 ≤ 3s → 超限 429）
  3. docker exec -t 容器 runner 用户执行：
       python: python3 - <<'EOF' … EOF
       shell:  bash -c '…'
  4. Exec 起 8s 定时器；到点：destroyExec → docker kill <容器> → 容器销毁重建
  5. 读 stdout/stderr（截 16KB）+ exitCode → 落审计 → 容器销毁回池
  6. 响应 {exitCode, stdout, stderr, durationMs, sandboxId}
```

### 3.3 容器池与并发

| 项 | 值 | 说明 |
|----|----|------|
| 池大小 | 默认 2（可配） | 闲置预热数 / 并发上限 |
| 获取 | 阻塞队列 + `take(3s)` | 3s 内无空容器 → 429（提示稍后再试） |
| 归还 | 执行完 **销毁再建新容器**（非直接复用） | 防止上一用户残留进程/文件污染下一位（租户隔离代办） |
| 池泄洪 | `@Scheduled` 5min 内无请求 → 清闲置容器 | 省资源 |

> 销毁重建代价 ≈ 0.5-2s；换取租户间干净隔离。P95 开始预算含此成本。

### 3.4 代码执行异常行为护栏

| 行为 | 处理 |
|------|------|
| 死循环 / 慢查询 | exec 8s 超时强杀 + 容器重建 |
| 无限输出 | stdout/stderr 截 16KB（管道带缓冲；超限后丢弃剩余） |
| 留后台进程 | 容器销毁即清理（孤儿进程随容器灭） |
| 读敏感文件 | 只读镜像内无 `/etc/shadow` 实体；`/proc` 受限；宿主路径不可达（无卷挂载） |

## 4. SQL 沙箱设计（SqlSandbox）

### 4.1 只读通道（硬边界）

| 层 | 机制 | 说明 |
|----|------|------|
| 账号 | PG 只读角色 `sandbox_ro`（仅授业务 schema 的 `SELECT`） | 无 INSERT/UPDATE/DELETE/DDL 权限，**硬写不进** |
| 连接 | JDBC URL 加 `?options=-c%20default_transaction_read_only%3Don` + `ApplicationName=sandbox` | 连接级只读兜底（第二道） |
| 事务 | 每次执行 `BEGIN READ ONLY; <sql>; COMMIT;` | 语句级只读（第三道，即便角色意外有写权限也被拒） |

### 4.2 AST 白名单（SqlSanitizer，JSQLParser）

| 项 | 规则 |
|----|------|
| 允许 | `SELECT`（含 `WITH CTE`） |
| 拒绝 | INSERT / UPDATE / DELETE / MERGE / TRUNCATE / DROP / ALTER / CREATE / CALL / COPY / DO / GRANT / REVOKE / VACUUM / ANALYZE / EXPLAIN(带 ANALYZE) / `SELECT ... FOR UPDATE` |
| 多语句 | JSQLParser 解析单个 statement；多个 `;` 截断前一条，其余拒绝 |
| 通配兜底 | 解析失败（语法脏）→ 拒绝并回错误（宁可误拦） |

### 4.3 强制 LIMIT 与结果脱敏

- **强制 LIMIT**：SELECT 无显式 LIMIT → 注入 `LIMIT 100`；有 LIMIT 则 `MIN(原有, 100)`。防全表扫描拉爆内存。
- **行数截断**：结果集 `maxRows` 100（JDBC 层面）；SQL 层 LIMIT 双保险。
- **敏感列过滤**：列名命中黑名单（`password`/`token`/`api_key`/`secret`/`credit_card`/`id_card`）→ 返回 `***`（脱敏占位）+ 审计告警。
- **返回结构**：`{columns:[...], rows:[[...]], rowCount, truncated}`。

### 4.4 表白名单（演进项，v1 放款）

- v1：会话内可查询所有**已授权业务表**（需在 `sandbox_ro` 授权列表），不做表级动态白名单；
- 演进（W15 语义层）：「语义层 schema → 允许表」映射驱动授权，未授权表 403。

## 8. 备选方案与取舍

| 方案 | 结论 | 理由 |
|------|------|------|
| 8.1 Java SecurityManager / 自定义 ClassLoader 沙箱 | ❌ | JDK 17 已 deprecated、攻击面大（反射/序列化逃逸多）；无网络/资源硬隔离 |
| 8.2 裸 ProcessBuilder 执行（无容器） | ❌ | 无网络/CPU/内存/文件隔离，子进程可访问完整宿主文件系统 |
| 8.3 gVisor / Firecracker 微虚拟机 | ⏭️ 演进 | 隔离天花板更高但部署运维复杂；v1 Docker 容器已满足红线，量大后再演进 |
| 8.4 SQL 沙箱只用 AST 白名单（无只读账号） | ❌ | 单点防线：AST 解析器有一处绕过即写库；连接级只读角色是"解析失败也写不成"的硬兜底 |
| 8.5 只读物理副本隔离查询 | ⏭️ 演进 | 数据一致性/成本；v1 用同库只读角色，规模后再上副本（W17 数据平台） |
| 8.6 池复用容器（执行完毕不改） | ❌ | 上用户残留进程/临时文件污染下一位→跨租户数据泄露风险；**销毁重建**保干净 |

## 9. 影响分析（必查）

### 9.1 租户隔离 ★红线
- **Sandbox 为什么是租户级隔离缺口？** 同一容器若被 A 用户跑过后 B 用户复用，A 的残留（`/tmp` 文件、后台进程）可能被 B 读到 → **跨租户泄露**。对策：**执行完销毁重建容器**（不共享）；`sandboxId` 每次唯一。
- SQL 沙箱走只读角色（平台级）+ 应用层以 `X-Tenant-Id` 注入 SQL 过滤（`WHERE tenant_id=?` 由服务拼入，禁止模型生成的完整 WHERE——v1 由调用方组装，W15 NL2SQL 语义层补强）。

### 9.2 数据血缘
- 审计记录 `tenant_id + sql_hash + sandbox_id + duration` 可回溯谁在何时执行了什么；输出脱敏列触发的 `dropped` 标志留痕。

### 9.3 PII / 数据脱敏
- SQL 结果敏感列黑名单脱敏（password/token/api_key/secret/card）；代码沙箱输出截断防数据外带。

### 9.4 保留策略
- 审计走日志滚动（30 天）；镜像随版本重建（不持久化容器）；`sandbox_ro` 授权配置随 DDL 幂等维护。

### 9.5 部署影响
- 平台 JVM 需能访问 Docker daemon（本机 docker socket 或 `DOCKER_HOST`）；`sboxes/python-311` 镜像需预先构建/拉取；CI 需起 Docker（GitHub Actions 原生支持）。

> v1.1 实现回写（2026-09-05）：
> - **代码沙箱后端定为 Docker CLI**（docker-java 在 Windows npipe 连接异常，CLI 跨平台/CI 可靠；运行时配置 `network none/read-only/限额/cap-drop ALL/非 root` 全部经 `docker create` 参数强制，细粒度一致）。
> - **镜像基础源走 daocloud**（`docker.m.daocloud.io/library/alpine:3.20` + 清华 apk 源——Docker Hub 直连超时）；本地已构建 `sboxes/python-311`。
> - **逃逸用例调整**：[7] 读 `/proc/1/environ` → 改为「写宿主内核参数(/proc/sys)」；[18] `kill -9 1` → 改为「进入宿主命名空间(nsenter -t 1)」——前者在容器内读取自身 PID1 属隔离内正常行为，非逃逸；换为真正验证隔离失败的场景。
> - **SQL 沙箱**：复用平台数据源但强制 `Connection.setReadOnly + BEGIN READ ONLY 事务只读`（当前不单独建只读账号，生产配置 `sandbox.sql-*` 指向只读账号更硬）；实测 `SELECT t_app` 返回数据、`DROP/INSERT` 返回 403。

> 红线提示：本设计逐项均为安全边界，获批前禁止实现；实现阶段任何偏离（如放宽 network none）必须回写本文档并经用户确认。
